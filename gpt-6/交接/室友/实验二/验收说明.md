# 实验二 常用网络命令和网络工具的使用

2026-11-18 已补 B 轮 Windows 11 命令窗口实拍，含公网和 VMnet8 的 ping、tracert、ipconfig 与 netstat。报告采用补拍图时，以截图索引记录的当次观测为准。XP 的 DHCP 和关联进程实拍待补。 [本轮命令实拍与说明](验收/命令实拍/截图索引.md)

## 环境与执行入口

本次是同一套实验环境的第二次运行。Windows 11 宿主用于公网探测，Windows XP SP3 用于隔离网命令与 DHCP，Ubuntu 18.04 用于验证局域网往返。Wireshark 4.6.9 在 VMnet1 捕获并回读。指导书以 Windows 7 和物理网卡为例，本次操作由上述虚拟环境完成。

- XP 原接口连接 `192.168.77.0/24` 私有网，测试时临时设 `192.168.77.3/24`，对端 Ubuntu 为 `192.168.77.2`。
- 第二块临时网卡 MAC 为 `00:50:56:2a:12:02`，只接入宿主 VMnet1。VMware DHCP 服务器为 `192.168.37.254`，宿主接口为 `192.168.37.1`，本轮客户地址为 `192.168.37.129/24`。释放与续租均显式指定 `Local Area Connection 2`。
- [LAB2.CMD](LAB2.CMD) 执行 DHCP、普通及大包探测、netstat。[LAN.CMD](LAN.CMD) 与 [PINGT.VBS](PINGT.VBS) 执行私有网操作。三个脚本从临时 FAT12 软盘执行并回写原始日志。结束后 XP 恢复原接口 DHCP 模式，卸载临时软盘和临时网卡，恢复原 VMX 并开机。

## 操作与实测

### 1. ping 帮助与参数

`ping /?` 用于查看帮助。普通 ping 发送 ICMP Echo Request，`-a` 请求名称解析，`-n` 控制发送次数，`-l` 设数据长度，`-t` 持续发包，`-r` 请求 IPv4 路由记录，`-f` 设置 DF。

- XP 到 Ubuntu 普通 ping 收到 4/4，应答 TTL 为 64。`-a -n 3 -l 64` 收到 3/3，连续 `-t` 有实际应答并在约 6 秒后由脚本结束。发送 5000 字节 Echo 数据收到 3/3。
- Windows 宿主对 `www.qq.com` 解析到 `120.233.51.33` 后普通 ping 收到 4/4，RTT 42–68 ms，TTL 49。`-a -n 3 -l 64` 收到 3/3。另跑公网 `-t` 约 6 秒，共记录 6 条应答。
- XP 向 VMnet1 宿主接口 `192.168.37.1` 发出了实际 Echo 请求，主包未捕获该接口的 Echo Reply。私有网正常应答另外实测。

证据见[图 1 局域网](验收/图01-局域网Ping.png)、[图 2 公网](验收/图02-公网Ping.png)、[图 10 帮助和持续 Ping](验收/图10-帮助与持续Ping.png)、[公网命令](验收/01-公网命令.log)、[公网持续 Ping](验收/02-ping-t.log)及[私有网日志](验收/05-XP-Ubuntu-LAN.log)。

### 2. ipconfig 释放和续租

执行帮助、`ipconfig` 和 `ipconfig /all`，读取地址、掩码、MAC 与 DHCP 服务器。指定临时网卡执行 Release，核对地址与掩码归零。第一次 Renew 得到 `192.168.37.129/24`；第二次 Renew 续用原租约，再释放变为 `0.0.0.0`。为后续分片再申请一次租约。见[图 3](验收/图03-IP配置释放续租.png)和[原始 XP 命令](验收/04-XP-DHCP-fragmentation.log)。

### 3. netstat 分析

`netstat /?` 查看帮助。`-a -n` 以数字地址列出监听及活动连接，TCP 135 和 445 的 `LISTENING` 表示端口等待连接。`-e` 提供接口收发字节和错误计数；`-s` 按 IPv4、ICMP、TCP、UDP 等协议显示计数，其中 IPv4 字段可检查分片。`-b -n` 记录进程尝试，再用 `-a -b -n` 查看监听项关联的程序，TCP 135 可核对 `svchost.exe`。见[图 4](验收/图04-Netstat统计与进程.png)及[隔离网输出](验收/04-XP-DHCP-fragmentation.log)、[私有网输出](验收/05-XP-Ubuntu-LAN.log)。

### 4. tracert 和 Record Route 对照

对同一个 `www.qq.com` 地址 `120.233.51.33`，`ping -4 -r 9` 4 次超时，`tracert -4 -d -h 24 -w 750` 在第 19 跳到达，多个中间跳显示星号。Record Route 要求沿途处理 IPv4 选项并随响应带回记录，tracert 发送不同 TTL 的探测，以 ICMP 超时响应和目标应答定位跳点。超时现象无法确定哪个设备处理了选项。另测 TEST-NET-1 地址 `192.0.2.2`，8 跳内未达，途中第 1、6、7 跳有应答。见[图 5](验收/图05-Tracert对照.png)及[命令日志](验收/01-公网命令.log)。

### 5. DHCP 抓包

主包共 44 帧，Dumpcap 报告 0 丢包。以 `dhcp.hw.mac_addr == 00:50:56:2a:12:02` 过滤出 14 条报文。

- 第 3 帧为 Release。第 4–9 帧事务号为 `0xa53f8597`，按 Discover、Offer、Discover、Offer、Request、ACK 排列。可见一次 Discover/Offer 重试，同一事务最终成功。
- 客户端尚未配置地址时，从 `0.0.0.0:68` 发往 `255.255.255.255:67`。服务器使用 `192.168.37.254:67` 向 `192.168.37.129:68` 返回 Offer 和 ACK。分配地址见 `yiaddr`，租期 1800 秒。
- 第 13、14 帧为已有地址上的单播 Request 和 ACK。第 15 帧为再次 Release。第 16–19 帧完成下一次 Discover、Offer、Request、ACK，供分片阶段使用。

见[图 6](验收/图06-DHCP事务.png)、[DHCP 字段](验收/06-DHCP.tsv)和[原始主包](验收/03-DHCP-IPv4.pcapng)。

### 6. IPv4 分片和指导书问答

1. **首个 ICMP。** 显示过滤器为 `ip.src == 192.168.37.129 && ip.proto == 1`。按 Source 排序并展开 IPv4 后，第 23 帧源地址是 `192.168.37.129`，目标是 `192.168.37.1`，协议值 1，首部 20 字节，总长度 60。有效载荷 `60 - 20 = 40`，包括 8 字节 ICMP 首部与 32 字节数据。MF=0 且偏移=0 表明该帧未分片。见[图 7](验收/图07-首个ICMP请求.png)。
2. **过滤后能看见哪些包。** 同一源地址下可看到后续探测。仅选 `icmp` 可能只显示重组后的 ICMP 条目，其他片可能显示为 IPv4。使用 `ip.proto == 1` 并按 `ip.id` 归组可查看四个分片。
3. **5,000 字节回显数据。** 第一组为第 33–36 帧，ID 均为 `0x00b2`。IP 总长度分别为 1500、1500、1500、588 字节。20 字节首部之外的有效载荷依次为 1480、1480、1480、568，字节偏移 0、1480、2960、4440，对应头部以八字节为单位的偏移 0、185、370、555。前三片 MF=1，尾片 MF=0。Wireshark 显示重组后 5008 字节。另两组为第 37–40、41–44 帧。见[图 8](验收/图08-IPv4首片.png)与[图 9](验收/图09-IPv4尾片与重组.png)。
4. **哪些字段变化。** 同一原始数据报的各片共享源地址、目标地址、协议和 ID。偏移与 MF 确定拼接顺序与末片，长度与首部校验和随分片变化。发往同一地址的独立请求中，第 23、24 帧 ID 从 `0x006d` 到 `0x0078`，校验和从 `0x6e81` 到 `0x6e76`；第 30 帧改用 64 字节数据后总长度增至 92。TTL 在本发送链路上均为 128，经过路由转发时可能变化。
5. **Identification。** 三个大请求的 ID 是 `0x00b2`、`0x00b3`、`0x00b4`。同一请求各片共享 ID，三个 ID 本轮碰巧连续。使用分片图和[IPv4 字段](验收/07-IPv4.tsv)验证。
6. **DF 对照。** 私有 LAN 的 `-f -l 1472` 成功，`-f -l 1473` 提示必须分片。边界从 `1500 - 20 - 8 = 1472` 得出，与实测一致。
