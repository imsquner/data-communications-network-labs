# 实验二 常用网络命令和网络工具的使用

2026-11-18 已补 A 轮 Windows 11 命令窗口实拍，含公网和 VMnet8 的 ping、tracert、ipconfig 与 netstat。报告采用补拍图时，以截图索引记录的当次观测为准。XP 的 DHCP 和关联进程实拍待补。 [本轮命令实拍与说明](验收/命令实拍/截图索引.md)

## 环境与复现入口

依据《实验2-v4.pdf》完成四项网络命令和两项抓包。指导书以 Windows 7 实验室为例。本次用 Windows XP SP3 来宾执行隔离网命令，用 Windows 11 宿主机执行公网探测。Wireshark 4.6.9 的 Dumpcap 在宿主机 VMnet1 接口录制，Wireshark 和 TShark 用于回读同一个 PCAPNG。

- **VMnet1 仅主机网**。XP 从 VMware DHCP 服务器 `192.168.37.254` 获得 `192.168.37.128/24`，宿主虚拟网卡为 `192.168.37.1`。这个网段用于租约和分片采集。
- **原有私有 LAN segment**。XP 临时设为 `192.168.77.3/24`，Ubuntu 为 `192.168.77.2/24`，用于验证局域网往返和 DF 边界。完成后 XP 恢复 DHCP，原虚拟机配置逐字节恢复后重新开机，确认两台实验虚拟机均在运行。
- **脚本**。[XP-LAB2.CMD](XP-LAB2.CMD) 执行租约、分片和 netstat。[XP-LAN2.CMD](XP-LAN2.CMD) 和 [XP-PING-T.VBS](XP-PING-T.VBS) 执行私有 LAN 测试。运行时经临时 FAT12 软盘映射为 `A:\LAB2.CMD` 与 `A:\PINGT.VBS`，原始命令输出回写软盘后按原字节导出。两份 CMD 对应各自的网段。
- **抓包入口**。直接用 Wireshark 打开 [08-DHCP与IPv4分片.pcapng](验收/08-DHCP与IPv4分片.pcapng)。按接口名选择 VMnet1，以 `(ether host 00:0c:29:ed:66:f6 or udp port 67 or udp port 68) and (arp or ip proto 1 or udp port 67 or udp port 68)` 为捕获过滤器。使用实际 XP 的 MAC 可同时保留非首片和 DHCP 广播。主包 40 帧，采集日志报告 0 丢包。XP 开机时的自动 DORA 另存于 [03-VMnet1原始抓包.pcapng](验收/03-VMnet1原始抓包.pcapng)，第一次手动采集覆盖租约与普通探测，主包使用随后完成的完整复跑。

## 实验过程和结果

### 1. ping

先执行 `ping /?` 核对参数。普通 ping 使用 ICMP Echo 验证往返。Windows 的 `-a` 请求反向解析，`-n` 设请求数，`-l` 设 Echo 数据长度，`-t` 连续发包直至停止，`-r` 请求 IPv4 Record Route，`-f` 设置 DF。 [Windows ping 文档](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/ping)

- XP 到 Ubuntu 的普通 32 字节 ping 收到 **4/4** 应答，TTL 64，耗时小于或等于 1 ms。`-a -n 3 -l 56` 收到 **3/3**；目标在日志中显示为 IP。私有网实际执行 `-t` 后约 6 秒结束，并留存连续应答。
- Windows 宿主对 `www.baidu.com` 的一次解析落在 `36.152.44.93`。普通 ping 收到 **4/4**，RTT 33–37 ms，TTL 50。`-a -n 3 -l 56` 收到 **3/3**。公网 `-t` 独立运行约 6 秒，DNS 该次选到 `36.152.44.132`，收到 6 条回复。公网帮助与早期路线探测保存在 [01-公网命令.log](验收/01-公网命令.log)，连续测试保存在 [02b-ping-t-公网.log](验收/02b-ping-t-公网.log)。
- VMnet1 上 XP 向 `192.168.37.1` 发送的请求出现在抓包中，记录期间没收到该地址的 Echo Reply，单凭这些数据无法确定未应答原因。私有 LAN 的 XP 到 Ubuntu 补测收到了正常往返。 [XP 私有网日志](验收/14-XP-Ubuntu-private-LAN.log) · [图 1 局域网 Ping](验收/图01-局域网Ping.png) · [图 2 公网 Ping](验收/图02-公网Ping.png)

### 2. ipconfig

在 XP 执行 `ipconfig /?`、`ipconfig` 和 `ipconfig /all`。普通输出含地址、掩码、默认网关，`/all` 还显示 MAC、DHCP 状态、服务器及租期。按指导书执行释放、申请、再次续租、再释放。释放后地址和掩码出现 `0.0.0.0`，重新申请后回到 `192.168.37.128` 与 `255.255.255.0`。末尾再次申请给分片采集建立基线。宿主网卡全程正常联网。 [XP 原始命令日志](验收/09-XP-复跑命令.log) · [图 3 释放与续租](验收/图03-IP配置释放续租.png)

### 3. netstat

在 XP 控制台执行 `netstat /?`、`netstat -a -n`、`netstat -e`、`netstat -s`、`netstat -b -n`，另用 `netstat -a -b -n` 显示侦听项对应程序。

- `-a` 包括活动连接和侦听端口，`-n` 保留数字地址和端口。复跑有 `0.0.0.0:135` 与 `192.168.37.128:139` 的 TCP 侦听，以及 UDP 端口条目。TCP 的 `LISTENING` 表示等候连接。UDP 行没有 TCP 连接状态。
- `-e` 显示接口接收、发送统计。复跑时字节计数为 44,137 与 56,399，错误数均为 0。`-s` 分别显示 IPv4、ICMPv4、TCP 与 UDP 计数。XP 在两次命令运行后累计成功分片 6 个数据报、生成 24 片，主抓包只覆盖后一次的 3 个数据报和 12 片。
- `-b` 查看关联的可执行文件。单独运行时仅显示连接表头，附加 `-a` 后看到侦听项及 `svchost.exe`、`System` 等名称。例如 `0.0.0.0:135` 对应 `svchost.exe`。 [XP 原始命令日志](验收/09-XP-复跑命令.log) · [私有网补测日志](验收/14-XP-Ubuntu-private-LAN.log) · [图 4 统计与进程](验收/图04-Netstat统计与进程.png)

### 4. tracert 与 ping -r 对照

同一轮用 `ping -4 -r 9 -n 4 -w 900 www.baidu.com` 和 `tracert -4 -d -h 22 -w 900 www.baidu.com`。两条命令都解析到 `36.152.44.93`。带 Record Route 的 ping 4 次超时，因而没有收到可展示的路由记录。tracert 在第 1、3、6、10 跳看见答复，在第 16 跳到达目标。中间星号表示相应探测在等待时间内未收到答复。Record Route 依靠 IPv4 选项被沿途处理并随响应返回，最多记录 9 个地址。tracert 发送不同 TTL 的探测并读取沿途 ICMP 超时响应。本次结果无法定位 Record Route 探测在哪一跳失去答复。 [同站点原始日志](验收/02-同站点路由对照.log) · [Windows ping 文档](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/ping) · [Windows tracert 文档](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tracert)

同时对文档保留地址 `192.0.2.1` 执行 `tracert -4 -d -h 8 -w 600`，8 跳范围内未到达目的地址，收到第 1、3、6 跳的答复。中间跳应答与目标可达是两种独立观测。 [图 5 两次路由探测](验收/图05-站点与不可达地址路由.png) · [RFC 5737](https://www.rfc-editor.org/rfc/rfc5737)

### 5. DHCP 帧分析

以 `dhcp.hw.mac_addr == 00:0c:29:ed:66:f6` 定位 XP。主包中，第 3 帧为 Release。第 4–7 帧按 Discover、Offer、Request、ACK 排列，事务 ID 一致为 `0xcbd1a3fc`。客户端未配置时用 `0.0.0.0:68` 向 `255.255.255.255:67` 广播，服务器 Offer 和 ACK 从 `192.168.37.254:67` 单播到 `192.168.37.128:68`。Offer、ACK 的 `yiaddr` 为 `192.168.37.128`，事务中通告掩码 `255.255.255.0`、租期 `1800 s`。Discover 还携带此前地址作为请求选项，服务器仍实际分配同一个地址。

已持有租约时的再次 `/renew` 对应第 11–12 帧，客户端用当前地址单播 Request，服务器单播 ACK。第 13 帧再次 Release，第 14–17 帧是随后用于分片试验的另一次完整分配。对应帧内可核对 UDP 67/68、事务 ID、客户端 MAC 与租约字段。 [DHCP 字段](验收/10-DHCP字段.tsv) · [图 6 DHCP 事务](验收/图06-DHCP事务.png) · [RFC 2131](https://www.rfc-editor.org/rfc/rfc2131)

### 6. IPv4 首部、分片与报告问答

1. **首个 XP Echo Request。** 使用 `ip.src == 192.168.37.128 && ip.proto == 1`，单击 Source 排序，选中第 21 帧并展开 IPv4。源地址 `192.168.37.128`，目的 `192.168.37.1`，上层协议值 1（ICMP），IHL 5 即 20 字节，总长度 60。IP 有效载荷为 `60 - 20 = 40` 字节，包括 8 字节 ICMP 首部与 32 字节 Echo 数据。偏移为 0、MF 为 0，这个数据报未分片。该样本的 ID 为 `0x00aa`，TTL 128。 [图 7 首个 ICMP 请求](验收/图07-首个ICMP请求.png)
2. **能看到哪些 ICMP。** 同一源地址下可继续看到该 XP 的其余请求。只按 `icmp` 过滤时，同一大请求的早期分片可能显示为 IPv4 并被排除，重组完成的帧显示为 ICMP。用 `ip.proto == 1` 保留该协议的全部 IPv4 分片，再用 `ip.id` 归组。当前源过滤排除了反方向报文；解除源过滤后，仍只能看到当前网卡和捕获窗口内出现的包。
3. **四片怎样拼合。** XP 向宿主虚拟网卡发出 3 次 `ping -l 5000` 请求。第一个大请求为第 29–32 帧，ID 都是 `0x00cf`。各片的 IP 总长度为 1500、1500、1500、588，首部均为 20，有效载荷为 1480、1480、1480、568，合计 5008 字节。偏移字段为 0、185、370、555，单位为 8 字节，Wireshark 展示的字节偏移为 0、1480、2960、4440。前三片 MF=1，尾片 MF=0。第 32 帧显示 Wireshark 成功重组为 5008 字节，即 8 字节 ICMP 首部与 5000 字节数据。原始未分片 IP 总长度为 5028。第 33–36、37–40 帧也各是一组完整的四片。 [图 8 IPv4 首片](验收/图08-IPv4首片.png) · [图 9 IPv4 尾片与重组](验收/图09-IPv4尾片与重组.png) · [RFC 791](https://www.rfc-editor.org/rfc/rfc791)
4. **字段为何变化。** 同一原始数据报的各片共享源、目的、协议和 Identification，重组端用这些字段分组。偏移定位每片的数据，MF 标识后续是否还有分片，总长度反映各片自身长度，首部校验和随首部变化重新计算。本样本中 TTL 都为 128，因为捕获的是同一发送端同链路数据，TTL 在经过路由器转发时会变化。IHL 均为 20 字节是本样本的属性，跨分片处理 IPv4 可选字段时需考虑选项的复制位。对照发往同一地址的独立请求，第 21、22 帧都是 60 字节，IP ID 分别为 `0x00aa`、`0x00b4`，首部校验和随之变化。载荷从 32 改为 56 字节时，第 26 帧的 IP 总长度增至 84；本次各请求的目标地址和上层协议保持一致，源地址也因同一网卡发送而固定。 [IPv4 字段](验收/11-IPv4字段.tsv) · [RFC 791](https://www.rfc-editor.org/rfc/rfc791)
5. **Identification 的观测。** 普通 Echo 的 ID 依次出现 `0x00aa`、`0x00b4`、`0x00be` 等，三条大 Echo 的 ID 分别为 `0x00cf`、`0x00d0`、`0x00d1`。同一大请求的四片 ID 一致；不同大请求可依 ID 区分。本次连续的三个 ID 是发送端观测，不代表协议规定必须逐一递增。 [主样本完整解码](验收/12-主样本完整解码.txt) · [RFC 6864](https://www.rfc-editor.org/rfc/rfc6864)
6. **DF 对照。** 在 VMnet1 上加 `-f -l 5000`，XP 提示 `Packet needs to be fragmented but DF set.`。私有 LAN 的 Ubuntu 对 5000 字节请求答复 3/3；加 DF 后，1472 字节 Echo 数据收到 1/1 应答，1473 字节超出 1500 字节 IP MTU，发送端给出相同提示。这个对照验证了 `1500 - 20 - 8 = 1472` 的本次上限。 [私有网原始日志](验收/14-XP-Ubuntu-private-LAN.log) · [图 1 局域网 Ping](验收/图01-局域网Ping.png)
